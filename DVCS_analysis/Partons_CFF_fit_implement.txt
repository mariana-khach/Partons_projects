  1. "Discarded scalar setup"

  Inside DVCSAluMinusSin1PhiTorch::computeTensor() (src/NNFit/theory/Modules/Obs/DVCS/DVCSAluMinusSin1PhiTorch.cpp:151):

  1. setKinematics(kinematic) ← this is the only step we need
  2. setExperimentalConditions(...)

 Plan: Torch reimplementation of the DVCSAluMinusSin1Phi observable chain

 Context

 We want to train a neural network that parametrizes DVCS CFFs directly on observable
 data (beam-spin asymmetry A_LU^{sin1φ}), which requires the gradient ∂A_LU/∂(NN weights)
 to flow through the whole PARTONS computation. PARTONS' scalar pipeline
 (DVCSObservableService → DVCSAluMinusSin1Phi → DVCSProcessBMJ12 → CFF module) returns
 plain doubles and breaks autograd at every step.

 The goal is a parallel Torch path that mirrors the scalar class hierarchy, keeps every
 step in torch::Tensor, and is registered/usable through PARTONS exactly like the scalar
 modules. Each Torch module also exposes a scalar wrapper (tensor result .item()-ed under
 NoGradGuard) so the same module doubles as a drop-in scalar module. The φ (harmonic)
 integral uses the already-built MathIntegratorModuleTorch with DEXP — the same
 integrator the scalar DVCSAluMinusSin1Phi uses — so the two paths agree to precision.

 What the scalar chain actually computes (verified)

 - DVCSObservableService::computeSingleKinematic(kin, pObs) → pObs->compute(...) → trivial.
 - DVCSAluMinusSin1Phi::computeObservable = integrate( A_LU(φ)·sin φ, 0..2π, DEXP ) / π.
 - DVCSAluMinus::computeObservable = (σ(λ=+1,Λ_t=-1) − σ(λ=−1)) / (σ(+1) + σ(−1)) with

❯ we are going to have multiple batches of data corresponding to different observables in the DVCS CFF training, will the pybind crossing of  N×20 times per epoch slow down the fitting?

Short answer: no — even N×20 crossings would only add milliseconds per epoch, and with multiple observables you shouldn't end up anywhere near that granularity anyway. Crossings should scale with the number of observables, not the number of data points.

The arithmetic on the crossing itself

A pybind11 call with tensor arguments costs on the order of 1–5 µs (argument marshalling + GIL; tensors pass zero-copy). Take a pessimistic fine-grained design at, say, N = 500 points: 500 × 20 = 10,000 crossings × ~3 µs ≈ 30 ms per epoch. Your current per-epoch physics cost is ~0.2 s for 16 points, so ~6 s at N = 500. The boundary overhead would be well under 1% — the crossing is never the bottleneck at physically plausible dataset sizes. The backward pass doesn't multiply this either: loss.backward() traverses the merged graph inside the C++ autograd engine in one go, regardless of how many calls built it.

The real cost of fine granularity (and it's not pybind)

What actually hurts about a per-point, per-φ-node structure is that it fragments the computation into thousands of 0-d tensor operations. Each ATen op carries a fixed dispatch overhead of a few µs, which dwarfs the arithmetic on tiny tensors — and that penalty exists identically in pure C++. This is exactly why speedup #3 (batching over data points) was already the plan for the C++ training loop before pybind entered the picture. So "keep the boundary coarse" is really "keep the tensors batched"; the pybind advice falls out of that for free.

How multiple observables fit this

Multiple observables don't force fine granularity — they change the crossing count from 1 to K (number of distinct observables), which is trivial:

- Group the data by observable. For each observable k with its N_k kinematic points, make one batched call per epoch: (CFFs or kinematics [N_k], …) → obs_pred[N_k].
- Each observable type gets its own batched entry point on the C++ side (the thin computeTensorImplBatch leaf from the #3 design — cross-sections and the batched φ-integral underneath are shared, so a new observable is only a new leaf, not a new stack).
- In Python: run the NN forward once (or once per group), call each observable's batched function, compute χ²_k per group, and sum: loss = Σ_k χ²_k. Autograd merges the K subgraphs at the shared NN parameters automatically; one backward() covers everything.

So a five-observable fit is ~5 crossings per epoch. Even 50 would be nothing.

One genuine scaling caveat

The thing that will grow your epoch time is the physics itself: total cost scales with Σ N_k × (cost per point of that observable), and cross-section-level observables are heavier than asymmetries built from ratios of the same σ's. If several observables share kinematic points (e.g., A_LU and a cos-moment on the same bins), design the C++ side so the prepare step (kinematics + 72 coefficients, given the CFFs) is computed once per unique kinematic batch and reused across observable leaves — that's the batched analog of the #1 hoist you already did for the two helicities, and it's worth building into the prepareBatch API from the start.

❯ should I implement parallel calculation of custom loss by parralelizing the calculation of observables via cffs so that they will run in parralel and then theirautograds wil be addex??

No — don't add thread-level parallelism for this. What you want ("their autograds get added") already happens automatically without threads, and the threading itself would buy little while introducing the exact hazards you identified in the #4 analysis. Let me separate the two things bundled in the question.

Gradient addition needs no parallelism

If you compute the K observable losses sequentially and sum them —

loss = χ²_ALU + χ²_ALL + …   # one scalar
loss.backward()               # one call

— autograd merges the K subgraphs at the shared NN parameters and accumulates the gradients correctly in a single deterministic backward pass. Gradient addition is a property of the graph structure (all K subgraphs hang off the same leaf tensors), not of how the forward calls were scheduled. Running the forwards in parallel would produce the same gradients, just with more machinery.

Why threading the observable calculations isn't worth it

Your module chain is stateful and not thread-safe. DVCSProcessBMJ12Torch caches kinematics and CFF tensors in members, m_prepared is a shared flag, DVCSCFFNNTorch holds per-call kinematic state (m_xi, m_t, m_Q2). The serial loop you'd be parallelizing is short. K is a handful of observables. The per-epoch structure is K batched calls, each internally parallel. 1. Implement #3 (batch over data points) per observable — this is where the real speedup lives, it's deterministic, and it's safe by construction.
2. 3. Sum the χ² terms, one backward(). Nothing else needed for the gradients.

The only scenario where I'd revisit threading: after batching, profiling shows the epoch dominated by many small observable batches (tiny N_k, large K) that individually can't fill the cores. Even then, the first fix is concatenating compatible observables into one batch (an observable-index column selecting the Fourier weight), not threads. Thread-level parallelism over cloned chains is the last resort, and I'd be surprised if you ever reach it at DVCS-dataset sizes.

I looked at the current shapes, and there's a genuinely minimal version of #3. The key observations from the code:

- The φ-dependent assembly (crossSectionBH/VCS/InterfTensor, C_I0n, …) is written as double × [M]-tensor expressions, e.g. m_cBH0[0] * cosn(0) and -(m_J + 2*m_K[0]*torch::cos(phi1)) / m_yeps (DVCSProcessBMJ12Torch.cpp:604-608).
- All the φ-independent state it reads is cached scalars: plain double members plus 0-d CFF tensors (DVCSProcessBMJ12Torch.h:96-120).
- The integrator collapses with an all-elements .sum() (MathIntegratorModuleTorch.cpp:218).

The least invasive design: let the batch dimension ride on the cached members

Torch broadcasting means [N,1] × [M] → [N,M]. So if the cached φ-independent quantities become [N,1] tensors while φ stays a [M] tensor on the last axis, every assembly expression already written produces the batched [N,M] result unchanged — the same code that today does 0-d/double × [M] → [M]. You batch the chain not by rewriting the physics, but by changing what shape the cached state has. Concretely:

1. Don't re-express the verbatim kinematic block — loop it and stack. This is the big invasiveness saving over the "full" #3 design. The BMJ12 kinematic block is pure grad-free double arithmetic; per point it costs microseconds. A new prepareTensorBatch(kins[N]) runs the existing scalar block once per point in a plain C++ loop, harvests the resulting doubles into std::vectors, and stacks them into [N,1] constant tensors. The transcribed-verbatim block (the part hardest to re-validate) stays byte-for-byte untouched. The expensive axis — grad-carrying tensor ops — becomes constant in N; the O(N) scalar loop is noise.

2. Add tensor mirrors of the doubles the assembly reads, rather than changing member types. Keep m_cBH0, m_Cang, m_J, m_yeps, m_K, m_cF, m_phaseSpaceBMJ, … as double members (so the setup block's writes are untouched), and add tensor twins filled at the end of prepare: 0-d in single-kinematic mode, [N,1] in batch mode. The assembly methods switch to reading the mirrors — a mechanical rename, no formula changes. Single-point and batched paths then share one assembly implementation instead of you maintaining two copies.

3. One batched NN forward. DVCSCFFNNTorch gets a batch variant of computeAllCFFsTensor taking [N,3] scaled inputs (the CFFNNModel forward is already shape-agnostic — this is a few lines) and returning [N,1] complex CFF tensors into m_CFFstd. In batch prepare, m_CFF[F][j] = cF[j]·CFFstd[F] works as-is with cF as an [N,1] mirror.

4. One character in the integrator. .sum() → .sum(-1) in integrateTorchQuadrature ([M]→0-d stays identical; [N,M]→[N]). Only the fixed-rule path needs this — DEXP can't batch anyway (its convergence test is per-scalar), which is exactly why #2 (GL-10) was a prerequisite.

5. The observable leaf comes almost for free. After prepareTensorBatch, the existing lightweight crossSectionTensor(λ, charge, φ) returns [N,M] automatically, so aLUTensor's elementwise (σ⁺−σ⁻)/(σ⁺+σ⁻) and the sin φ moment weight broadcast unchanged. computeTensorImplBatch on DVCSAluMinusSin1PhiTorch is essentially "call prepareTensorBatch instead of prepareTensor, same integrand, result is [N]".

6. Additive entry points only. prepareTensorBatch next to prepareTensor in DVCSProcessModuleTorch; computeManyKinematicTorch next to computeSingleKinematicTorch in the service mixin; CustomLoss::forward swaps its row loop for one batched call and χ² = (((pred−y)/σ)²).sum(). Nothing on the scalar-virtual side or the single-kinematic tensor path is modified — the drop-in contract and all three observ_calc* verification paths keep working untouched.

❯ for doing fitting Hybrid with a pybind11 binding at the CFF seam —  where should the data for different observable used in training live, in C++ or Python?

In Python — all of it: kinematics, measured values, errors, observable grouping. The C++ side should hold no data at all, only cached derived kinematic state. This follows directly from where the loss lives.

Why the data belongs on the Python side

The loss is computed where the data is. In the CFF-seam design, Python owns the NN, the χ² assembly, and backward(). The measured values y and errors σ are consumed only in χ² = Σ((pred − y)/σ)² — a pure Python/torch expression. Pushing y/σ into C++ would mean binding a loss function too, which re-creates the current CustomLoss architecture and defeats the point of the seam.

The C++ side should be a pure physics function. Its contract is (kinematics, CFF tensors) → predicted observable [N]. The moment it knows about data files, train/val splits, or replicas, it stops being a reusable evaluator and becomes a fitting framework again. Keeping it data-blind is what makes it equally usable for fitting, for scans, and for plotting bands later.

Everything you plan to do to the data is trivially Python. MC replica fluctuation (y + σ·z, seeded per replica), train/validation splitting, per-observable grouping, cuts, residual plots — with data in Python, the whole replica-ensemble plan becomes a loop in the driver script with zero C++ changes, versus the training-code modification it requires today.

The resulting division of responsibility

At fit setup (once):
- Python loads each observable's dataset (pandas is fine): kinematics X_k = (xB, t, Q², E, φ)[N_k], values y_k, errors σ_k.
- For each observable group, Python constructs a bound evaluator (the batched *Torch observable chain) and hands it only the kinematics. The C++ side runs the loop-and-stack kinematic prepare once and caches the [N_k,1] mirrors.

This exploits a structural fact of the CFF seam: with CFFs injected from outside (prepareTensorWithCFFs), the kinematic block no longer depends on the NN, so it's constant across the entire fit — computed once per group at setup, not once per epoch. (In today's C++-internal-NN design it re-runs per epoch because prepare includes the NN forward; the seam removes that coupling.)

Per epoch:
cffs = net(X_scaled)                      # one [N_total, n_cff] forward, Python
loss = sum(
    chi2(evaluator_k(cffs[rows_k]),      # C++: cached kinematics + CFFs → obs [N_k]
         y_k, sigma_k)
    for k in groups)
loss.backward()                           # one backward through the merged graph

Only CFF tensors cross the boundary going in and prediction tensors coming out — K crossings per epoch, kinematics and data never cross after setup.

The one thing that legitimately lives in C++

Cached derived kinematic state (the BMJ12 doubles stacked into [N,1] mirrors, form factors, angular coefficients) — that's computation output, not data, and holding it per evaluator instance is exactly the batched analog of your #1 hoist. If you want reproducibility bookkeeping (which points, which fluctuation seed, which replica), record that in Python alongside the exported model — e.g., in the per-replica JSON — not in the C++ layer.

One practical note: keep the per-group evaluators as separate bound objects rather than one shared chain re-prepared per group — the prepare-state is modal (last-prepare-wins, as discussed), and per-group instances make the cached [N_k,1] state trivially safe with no re-prepare cost.

Changing the NN architecture: strongly favors the hybrid

In the all-C++ setup, an architecture change touches four places that must stay consistent:
1. CFFNNModelImpl (edit + recompile),
2. export_model_json() — it hardcodes the fc1/fc2 two-layer structure,
3. the hand-written numpy forward in the notebook — it hardcodes tanh(x@W1ᵀ+b1)@W2ᵀ+b2, and must be re-derived and re-validated (the ~5e-6 check) for every new topology,
4. anything reading the JSON schema.

That JSON + duplicated-forward bridge is the fragile link: it silently breaks the moment the architecture stops being "3→6(tanh)→n". In the hybrid, an architecture change is editing a torch.nn.Sequential in the driver script — no recompile, no export format, no duplicated forward (the model object used in training is the one used in plots), and torch.save/state_dict handles any topology. Since the CFF seam makes the C++ side NN-agnostic (CFFs in → observable out), the C++ code doesn't even know the architecture changed. The BMJ12 chain lives in C++ under both options, so a physics edit is the same edit, same rebuild, and — crucially — the same validation: the observ_calc* cross-check harness against base PARTONS stays in C++ and remains your gate regardless. - After a physics rebuild you reload the extension (fine in scripts; in Jupyter it means a kernel restart) — a minor friction the pure-C++ path doesn't have.

❯ does each new physics implementation require corresponding pibind wrapping and rebuilding the project?Is this a lot of work?

Short answer: every physics edit requires a rebuild (that's C++, and it's the same rebuild you do today), but almost none of them require touching the binding — if the binding is written at the right altitude. That's a design choice you make once, and your existing architecture makes it nearly free.

Why the binding stays untouched: bind the abstract chain, not the leaves

The trick is to exploit exactly the machinery you already built — the PARTONS registry plus base-typed virtual dispatch. The binding should expose one generic evaluator, roughly:

ev = ObservableEvaluator("DVCSAluMinusSin1PhiTorch",   # registry name
                         kinematics)                    # [N] points, prepared once
pred = ev(cff_tensor)                                   # [N], grad-carrying

Internally that's: BaseObjectRegistry lookup by name → base-typed DVCSObservableTorch* → computeTensorBatch through virtual dispatch. The binding never mentions a concrete leaf class. Consequences:

- New observable leaf (say DVCSAluMinusCos0PhiTorch): you write the C++ leaf exactly as you would today — it self-registers via classId — and rebuild. From Python it's available immediately as a string: ObservableEvaluator("DVCSAluMinusCos0PhiTorch", kins). Zero binding changes.
- Physics edit inside existing classes (a coefficient fix, porting the LP/TP sectors, a new sub-process implementation): implementation detail behind an unchanged interface. Zero binding changes, just rebuild.
- New process module: same story if module selection is also by registry name (a constructor argument or config call on the evaluator).

This is the same "add a leaf, reuse everything below" property your scalar and tensor chains already have — the binding just inherits it, because pybind11 wraps interfaces, not implementations.

When you do touch the binding

Only when the shape of data crossing the boundary changes:

- The CFF vector layout changes (e.g., adding twist-3/transversity components beyond the 8) — the evaluator's input convention updates.
- A new kinematic channel (TCS, DVMP) with a different kinematic type — a second evaluator class instantiated from the same generic template.
- You want a genuinely new capability exposed (e.g., returning per-φ cross sections for diagnostics).

Each of these is a handful of py::class_/.def(...) lines — the entire binding surface for this project is maybe 5 entities (PARTONS init/close, the evaluator, a config knob or two), a one-time file on the order of 100–200 lines. Amending it is minutes of work, and these events are rare — they correspond to changing the physics interface, which you'd design carefully anyway.

The rebuild itself: same cost as today

The extension is just another CMake target compiling the same src/NNFit/Theory/... sources (or linking them as a shared library) — add it to CMakeLists.txt once, next to Run_CFF_NN_Fit. After a physics edit: make (same incremental compile you do now), then restart the Python kernel or rerun the script. That kernel restart is the only workflow step you gain over pure C++ — and against it you drop the recompile-rerun-export-reload cycle for every NN/training/plotting change.

So the honest accounting: one-time cost of writing the binding module + CMake target + the ABI smoke test (a day-ish of careful work, mostly the ABI verification); recurring cost per physics change ≈ what you pay today plus a kernel restart; recurring cost per NN or analysis change ≈ near zero, versus a full C++ cycle now. For an analysis phase where physics changes are occasional and NN/analysis changes are constant, that trade is decisively in the hybrid's favor.




❯ will the replica fits run in parrallel with different partons sessions?

Quick check of the runtime config to ground the answer on log/output collisions:

  Searched for 1 pattern, read 1 file, ran 1 shell command

Yes — as long as the parallelism is at the process level, which is the plan (shard replica ranges across Run_CFF_NN_Fit invocations). Each OS process gets its own Partons::getInstance() singleton — its own registry, services, and logger — so N shards are N fully independent PARTONS sessions that never interact. This is exactly how your Gepard farm workflow parallelizes too (independent jobs). Within a single process the answer is no: PARTONS is a singleton, one session per process — but there's no reason to want that, since in-process thread parallelism over replicas was already ruled out.

I checked the runtime config for shared-resource collisions; it's in good shape:

- Logging: logger.properties has print.mode = COUT, not FILE — so there's no shared log file to clobber. Just redirect each shard's stdout separately (./bin/Run_CFF_NN_Fit 0 25 > rep_0-24.log 2>&1 &), otherwise interleaved output in one terminal is the only nuisance.
- Config files: partons.properties/logger.properties are read-only; any number of processes can share them. All shards must launch from DVCS_analysis/ (the known CWD quirk), which they naturally do.
- Outputs: the per-replica suffixing (cff_model_<r>.json, cff_learning_curve_<r>.csv, …) makes shard outputs disjoint as long as the CLI ranges don't overlap. The one collision point is the shared replica_summary.csv append — concurrent appends from multiple processes can interleave mid-line. Simplest fix: write one summary per shard (replica_summary_<r0>_<n>.csv) or even per replica, and concatenate in the Python aggregation step.

Two things to set deliberately when sharding:

1. Core budget. computation.nb.processor = 1 is already set (and the training path doesn't go through PARTONS' thread pool anyway), but libtorch defaults to using all cores for intra-op parallelism in every process — 8 shards × all-cores ATen = heavy oversubscription. Call torch::set_num_threads(1) (or cores/n_shards) at startup when running many shards; it's the same discipline as the OMP_NUM_THREADS block at the top of your Gepard farm script. For the current small per-replica tensors, 1 thread per process and more processes is the right trade.
2. Seeding under the retry policy. With per-replica seeds plus Gepard-style in-loop retry, a retried replica must draw fresh randomness — derive the seed from (base, r, attempt) (or just record whatever seed was actually used in the JSON) so shards stay reproducible without two shards ever sharing a stream.

The same answer carries over to the hybrid setup later: one PARTONS init per Python process, parallelism via a SLURM array or multiprocessing with spawned processes — never threads sharing one interpreter/PARTONS instance.

❯ if I keep analysis inside c++ and don't use a wraper, is there a functionality that I'll miss?

Short honest answer: no hard capability gap — everything in your program can be done in pure C++. libtorch's C++ API has the full autograd engine, nn::Module, Adam/SGD, serialization; your chain already proves the physics side. What you lose is not possibility but three specific things, in descending order of daily pain:

1. The iteration loop (the real loss)

Every experiment — new architecture, new lr, different dataset, different observable mix — becomes edit → recompile → relink → rerun instead of re-running a notebook cell. No REPL, no poking at a trained model interactively, no "plot the loss landscape around the minimum real quick," no inspecting a misbehaving replica's weights mid-session. This is workflow speed, not functionality, but over a year of analysis it's the dominant cost.

Mitigation that recovers most of it: make the C++ fitter fully config-driven — a config file specifying dataset path, output dir, lr/epochs/patience/seed, output-layer list, and the architecture as a layer list (a small factory building an MLP from [3, 16, 16, n] + activation names covers every architecture you're realistically going to try for 8 CFFs from 16–200 data points). Then "change the NN" is a config edit + rerun, no recompile. This single investment closes maybe 70% of the gap with Python.

2. Python-only training ecosystem

Concretely missing from the C++ API, with severity:

- torch.compile — Python-only. Irrelevant at your scale (your ops are tiny; the bottleneck is chain structure, not kernel dispatch).
- Optimizer/scheduler zoo — C++ has Adam/AdamW/SGD/RMSprop/LBFGS and only basic LR schedulers. No cosine-with-restarts, Lion, etc. For χ² fits of small MLPs, Adam + early stopping (what you have) is genuinely sufficient; LBFGS in C++ is actually available and often excellent for small-parameter χ² fits — arguably an argument for C++.
- Hyperparameter search frameworks (Optuna, Ray Tune) — you'd replace with a shell loop over config files + a results CSV. Cruder, workable.
- Experiment tracking (W&B, tensorboard integration) — your learning-curve CSVs + notebook plots substitute at small scale.

None of these is critical for your problem size. They matter at "hundreds of runs, big models" scale, not "6-hidden-unit MLP, 16–200 points."

3. Data-side and statistics conveniences

- gpddatabase: has a C++ interface, so access itself isn't lost — but expect the Python API to be the better-documented, primary-maintained one; uncertainty combination and dataset exploration will be clunkier in C++.
- pandas/scipy/sklearn for post-fit statistics (R², pulls, correlation matrices across replicas, outlier tests): you'd either hand-roll in C++ or — better — keep doing what you already do: write per-replica results to files, analyze in notebooks. Your existing CSV/JSON-export + Jupyter pattern already outsources plotting and statistics to Python without a wrapper. That pattern scales fine to replica ensembles.

What you genuinely don't lose

Worth stating explicitly: autograd and training (identical engine), speed (C++ is the fast path; the wrapper only ever matched it), replica orchestration (a C++ loop or shell script over --replica r --seed s), all physics and PARTONS integration, the deployment direction (replicas → PARTONS CFF modules — that was file-based regardless), and reproducibility (arguably better: one language, one toolchain, no pinned dual environment).

Verdict

The pure-C++ path is a legitimate choice, and it's the simpler system. The trade is: you accept a slower experiment loop and forgo Python's training ecosystem (mostly irrelevant at your scale), in exchange for zero environment coupling and one language. If you do choose it, two investments are non-negotiable to keep it livable: (1) the config-driven fitter + architecture factory above — no hyperparameter or architecture change should ever require compilation; (2) keep the file-export → notebook pipeline as the analysis surface, so statistics and plotting stay in Python where they're cheap — files as the boundary instead of pybind. That hybrid-via-files is genuinely workable; many lattice/pheno groups run exactly that way for years. The wrapper's unique, unreplicable offer remains just one thing: training driven from Python — valuable if architecture experimentation becomes your daily activity, skippable if the config-file factory covers your actual range of experiments.

if we decide to vectorize calculation of observabel in cff training, can we still keep modules in torch chain compatible with original chain?

Yes — and this was already the explicit design decided (see the CLAUDE.md "2026-06-22 #3 design decisions" notes), specifically so it wouldn't break the existing scalar/PARTONS drop-in contract. The key idea: the batched path is purely additive, not a replacement.

How compatibility is preserved:

1. New methods added to the same registered modules, not new modules. DVCSCFFNNTorch, DVCSProcessBMJ12Torch, DVCSAluMinusSin1PhiTorch each get a third sibling API (a batched [N]-tensor method) alongside the two that already exist: the scalar PARTONS virtual (computeCFF/computeObservable) and the single-kinematic tensor method (computeCFFTensor/computeTensor). Nothing about the existing two is touched.
2. The scalar virtuals are untouched. They still wrap the single-point tensor method under NoGradGuard+.item(), exactly as today — so PARTONS' normal scalar pipeline (and anything relying on the drop-in contract, e.g. polarized-target observables via base classes) is unaffected by whether a batched path exists.
3. Formulae aren't re-derived, they're made shape-polymorphic. The one piece of the chain that's currently hand-written as scalar doubles — the verbatim BMJ12 kinematics block in setupKinematicsTorch — has to become [N]-tensor arithmetic (same formula, tensor instead of double). Once it is, the existing single-kinematic path can just call it with N=1, collapsing what would otherwise be two parallel implementations into one. The CFF bilinear/linear layers and cross-section assembly are already tensor ops, so they broadcast from [Nφ] to [N,M] for free.
4. Service layer mirrors the scalar pattern: add computeManyKinematicTorch alongside the untouched computeSingleKinematicTorch, exactly like PARTONS' own computeSingleKinematic/computeManyKinematic pair — so it's additive at that layer too.
5. Verification gate, not just intent: N=1 batch result must equal the existing single-kinematic result, and full-batch χ² must equal the current per-point-loop χ² in CustomLossImpl::forward. That's the concrete check that compatibility actually held, not just "should."

Net effect: adding vectorization doesn't require touching observ_calc(), observ_calc_torch_scalar(), or anything driving the scalar PARTONS pipeline — those keep working unmodified. Only CustomLossImpl::forward's per-row loop (CustomLoss.cpp:85-104) would actually switch to calling the new batched entry point instead of looping computeSingleKinematicTorch per row — that's the one true consumer-side change needed to realize the speedup.
