In order to keep the observable calcualtion via Pytorch inside Partons, I have modified the files created for observable calculation via pytorch tensors stored in inside NNFit/theory and called inside CFF_NN_Fit.cpp in observ_calc_torch() function. I have also created new folders inside theory/ to mimic Partons structure and have moved NNFit/DVCSCFFNNPytorch.h and .cpp inside it. For the gradient flow to be preserved we can't use DVCSObservableService::computeSingleKinematic() used in scalar path and instead  differentiable path bypasses the service and calls computeTensor() directly on the registered observable subclass.

Th modifications are the following:
   
     Inside NNFit/DVCSCFFNNPytorch add computeCFFTensor() returning torch::Tensor for differentiable use, and have the existing computeCFF() call it and convert. PARTONS still works, plus a differentiable entry point for the theory submodule to conserve gradient flow.

  - Rewrite computeCFF() to be a 3-line wrapper: call computeCFFTensor(), .item<float>() the Re/Im components, return std::complex<double>.
  - One code path, used by both PARTONS and the theory submodule. Guaranteed numerical agreement by construction.
  - Small cost: the PARTONS path now builds an autograd graph it immediately throws away (negligible for a single forward pass, but real if you're calling it in a tight loop).
  
Build it in three steps, smallest first — (1) computeCFFTensor() in DVCSCFFNNPytorch, (2) a DVCSProcessBMJ12Torch subclass wrapping the existing DVCSAmplitudesBMJ12Torch, (3) a DVCSAluMinusSin1PhiTorch PARTONS-subclass wrapping the existing theory-submodule observable.
